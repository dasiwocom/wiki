# 为什么同样的代码生成的 hex 不一样

## 一句话

**hex 本来就不该用来逐字节对比。** 编译器版本、优化等级、授权状态任何一个不同，生成的字节就会不同——其中"未授权"这一项影响最大，它会把整个程序挪到 `0x0800` 地址开始。

## 先搞清楚 hex 是什么

C 源码编译之后并不能直接烧进芯片，要先变成一种叫 **hex 文件**的东西（后缀 `.hex`）。它记录的是"哪个地址放哪个字节"，本质是一张地址—数据的对照表。

烧录软件（比如 STC-ISP）打开 hex 后，会把内容填进一个叫 **Code Buffer** 的窗口显示出来。窗口左边是地址，右边是这个地址上的字节。芯片里没用到的空白地址，软件会填成 `FF`——`FF` 不是代码，只是"这里是空的"的意思。

所以 Code Buffer 里看到大片 `FF` 完全正常，真正有效的代码通常只占开头一小段。

## 四种原因，前三种都无所谓

| 原因 | 影响 |
| --- | --- |
| 编译器版本不同 | 同样一句 C，不同版本编译出的机器指令可能不同 |
| 优化等级不同 | 开不开优化、开到几级，生成的代码差别很大 |
| 编译时间不同 | 有些编译器会把时间戳写进去 |
| **Keil 未授权** | 不只是字节不同，而是**整个程序的地址被挪位**——下面单独说 |

前三种只影响"字节长得不一样"，**功能完全一样**。所以只要烧进去板子跑对了，hex 不一样根本不用管。

## 未授权时为什么会整体偏移

未授权（评估版）的 Keil C51 有两重限制：

1. 代码体积限制在 **2KB**
2. 程序被固定放到 **`0x0800`** 地址开始

于是 Code Buffer 变成这样：

```
0000h: 02 08 00          ← 只有一条跳转指令（跳到 0800h）
0003h ~ 07FFh: FF FF ... ← 一大片空白
0800h: 真正代码从这里开始
```

而授权之后是连续排布的：

```
0000h: 02 00 03   (LJMP 0003)
0003h: 启动代码
...
```

注意授权之后代码也不是从 `0000h` 开始——开头那十几个字节是编译器自动加的**启动代码**（清零内存、设置堆栈，然后才跳进 `main`）。这是所有 C 程序都有的，属于正常现象。

## 怎么确认自己是不是未授权

看编译后生成的 `.m51` 文件（链接清单，在工程的 Listings 目录下），里面有明确的一行：

```
RESTRICTED VERSION WITH 0800H BYTE CODE SIZE LIMIT
```

构建日志里的授权信息也会显示为 `LIC=----`（没有许可证号）。**看到这两处任意一处，就是未授权。**

## 需要担心吗

| 方面 | 影响 |
| --- | --- |
| 烧录和运行 | 没有影响，程序照常跑 |
| 和教程对比 hex | 排布不同，逐字节对比必然对不上 |
| 可用空间 | 评估版限制 2KB，而常见芯片有 8KB 甚至更多，学习阶段够用 |

> [!warning] 别用「对比 hex」来验证代码对不对
> 判断代码对不对，唯一标准是**烧进去看现象**。逐字节比对 hex 是无效验证——两个人就算用的是同一份源码、都授权了，只要 Keil 版本不同，字节照样不一样。

> [!note] 激活之后必须重新编译
> 激活 Keil 之后要**重新 Build**（不是只编译改动的文件），并且确认工程设置里勾选了生成 HEX 文件；烧录软件也要**重新打开一次** hex 文件，否则加载的还是旧文件。
